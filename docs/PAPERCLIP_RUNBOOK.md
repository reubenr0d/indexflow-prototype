# Paperclip Local Install Runbook

Step-by-step install + first-heartbeat + post-install housekeeping for the optional [Paperclip](https://paperclip.ing) operator dashboard. The repo is the **source of truth** — Paperclip is a layer on top that imports [`../COMPANY.md`](../COMPANY.md), schedules heartbeats via a shell adapter, and surfaces tickets / approvals / cost budgets from a web UI.

> **Scope reminder**: Paperclip manages the **engineering meta-agents** and (eventually) the **growth/ops agents**. Trading agents (`vault-manager`, `mining-manager`, `quality-matrix-manager` + the trading `risk-officer`) stay repo-managed via [`../scripts/agent-runner.mjs`](../scripts/agent-runner.mjs) + [`../.github/workflows/vault-agent.yml`](../.github/workflows/vault-agent.yml). The scope boundary is enforced by `COMPANY.md` §Out of Scope and the `scope_boundary` hard constraint.

This runbook is the *operator's* workflow — it's not a thing an agent runs. Per [`../AGENTS.md`](../AGENTS.md), agents must not deploy infrastructure or modify config without explicit user approval, so the operator (Reuben) does every step in this file.

## Mental model — what runs where

Paperclip has three layers of setup, plus a **repo-side mirror** that bridges our canonical agent layout to the plugin's required layout. **They're separate, sequential, and each leaves the layer above empty until you do the next step.** Confusing the layers is the #1 source of "why isn't my stuff there yet?" moments.

```
┌─────────────────────────────────────────────────────────────────┐
│  Layer 3: COMPANIES                                             │
│  (your IndexFlow org chart, employees, routines, budgets)       │
│  ↑                                                              │
│  │  imported by                                                 │
└──┼──────────────────────────────────────────────────────────────┘
   │
┌──┼──────────────────────────────────────────────────────────────┐
│  ↑  Layer 2: PLUGIN                                             │
│  │  (paperclip-agent-companies-plugin scans a source root for   │
│  │   COMPANY.md + agents/<slug>/AGENTS.md per its v0.9.x layout)│
│  ↑  installed into                                              │
└──┼──────────────────────────────────────────────────────────────┘
   │
┌──┼──────────────────────────────────────────────────────────────┐
│  ↑  Layer 1: INSTANCE                                           │
│     (Paperclip server + Postgres + workspace + LLM provider)    │
│     bootstrapped by `npx paperclipai onboard --yes`             │
│     then web-UI `/onboarding` for workspace+LLM choice          │
└─────────────────────────────────────────────────────────────────┘

  ▲   reads from
  │
┌──┴──────────────────────────────────────────────────────────────┐
│  Layer 0: REPO-SIDE MIRROR (paperclip/companies/indexflow/)     │
│  Generated by `npm run sync:paperclip` from the canonical       │
│  COMPANY.md + agents/*.md. The mirror exists because our        │
│  canonical layout is flat (agents/<slug>.md) but the plugin's   │
│  v0.9.x classifier requires agents/<slug>/AGENTS.md per-slug    │
│  subfolders. The mirror is git-tracked so GitHub-URL sources    │
│  work too.                                                      │
└─────────────────────────────────────────────────────────────────┘
```

**Three surprises to expect** (all are correct behaviour, not bugs):

1. After Phase 1, the dashboard shows an **empty workspace with no companies**. That's because nothing has been imported yet. Layer 1 is up; Layer 2 doesn't exist; Layer 3 has nothing to populate.
2. After Phase 2, the dashboard is **still empty** — the plugin is loaded but you haven't told it where to look. A new **Settings → Repository Catalog** menu item appears (older docs call this "Agent Companies"); that's the only visible change. Layer 2 exists now but you haven't connected it to a source yet.
3. If you point the source at the **repo root** instead of the **mirror subdir**, the plugin discovers the canonical `COMPANY.md` but classifies every `agents/*.md` file as unrecognised. The Discover panel shows the company but reports **"No structured contents detected"** and Import fails with **"Company not found."** — that's the v0.9.x classifier mismatch. Always point at `paperclip/companies/indexflow/`.

The IndexFlow org chart only materialises at Phase 4 (sync mirror → add mirror as source → Discover → Import).

## Phase 1 — Install Paperclip (~5 min)

The recommended path is the interactive onboarding wizard, which manages an embedded PostgreSQL automatically.

### Step 1a — CLI onboarding (infrastructure)

```bash
npx paperclipai onboard --yes
```

This single command:

- Creates config at `~/.paperclip/instances/default/config.json`
- Creates embedded PostgreSQL at `~/.paperclip/instances/default/db`
- Creates local file storage at `~/.paperclip/instances/default/data/storage`
- Boots the server at **`http://localhost:3100`** (Paperclip binds `127.0.0.1` in `local_trusted` mode — no login, single-user on your machine)

Run `npx paperclipai doctor` anytime for diagnostics. (Bare `paperclipai` won't be on PATH after an `npx`-style install — see Phase 2 for the PATH gotcha.)

### Step 1b — Web-UI onboarding (workspace + LLM provider)

Open `http://localhost:3100` in a browser. **First visit redirects to `http://127.0.0.1:3100/onboarding`** — that's a separate, web-UI first-time wizard for things the CLI can't sensibly pick a default for:

- **Workspace name** — any name you like (e.g. `IndexFlow` or `reuben-local`)
- **Default LLM provider** — pick whichever you actually use (Anthropic / OpenAI / OpenRouter / local). Either paste your API key now or pick "configure later" and add via Settings → Secrets in [Phase 3](#phase-3--wire-the-secrets-the-shell-adapter-needs-5-min).
- Accept all other defaults.

> The CLI's `--yes` only accepts defaults for the **infrastructure** layer (DB type, storage, host, port). Workspace name + LLM provider are workspace-level business choices the web wizard handles. Both wizards are expected — they're not a duplicate.

### What you should see after Phase 1

✅ Dashboard loads with an **empty workspace** (no companies, no employees, no runs). That's correct — see the [Mental model](#mental-model--what-runs-where) above. Layer 1 is live; nothing has been imported yet. Phases 2 + 4 fix this.

### Phase 1 alternatives

| Path | When to use |
|---|---|
| **Docker** (`docker compose -f docker-compose.quickstart.yml up --build` from a cloned Paperclip repo) | You want full isolation and don't want Node on the host |
| **Manual** (`git clone https://github.com/paperclipai/paperclip.git && cd paperclip && pnpm install && pnpm dev`) | You plan to contribute to Paperclip itself |
| **External Postgres** (`DATABASE_URL=postgresql://...` env var to either method) | You're prepping for production deployment later — defer this for the local-test step |

### Phase 1 troubleshooting

| Symptom | Fix |
|---|---|
| `Port 3100 already in use` | `PORT=3200 npx paperclipai run` (or pick any free port) |
| `zsh: command not found: paperclipai` | The `npx paperclipai onboard --yes` install caches the binary inside `~/.npm/_npx/<hash>/node_modules/.bin/`, **not** on global PATH. Always prefix `npx`: `npx paperclipai <command>` |
| `pnpm: command not found` | `npm install -g pnpm` then re-verify |
| `Node version too old` | See pre-flight steps above |
| Server starts but UI shows DB errors | `rm -rf ~/.paperclip/instances/default/db && npx paperclipai run` (nukes data) |
| Browser sits on `/onboarding` forever | The web wizard requires an LLM provider choice even if `--yes` ran cleanly on the CLI side — pick one (or "configure later") and proceed |
| Dashboard is empty after onboarding completes | **Expected** — Phases 2 + 4 populate it. See the [Mental model](#mental-model--what-runs-where) and "What you should see after Phase 1" above. |
| Anything else | `npx paperclipai doctor --repair` |

## Phase 2 — Install the agent-companies plugin (~2 min)

The plugin discovers `COMPANY.md` (`schema: agentcompanies/v1`) and turns it into a Paperclip company.

**Use Paperclip's own plugin CLI via `npx` — NOT `pnpm add`.** `pnpm add` would install the package as a project dependency in your shell's `node_modules`, which is not how Paperclip discovers plugins. Use `npx` (rather than bare `paperclipai`) because the `npx paperclipai onboard --yes` install in Phase 1 caches the binary inside `~/.npm/_npx/<hash>/node_modules/.bin/` and does **not** put it on your global PATH — typing `paperclipai` directly in a fresh shell will fail with `zsh: command not found: paperclipai`.

```bash
npx paperclipai plugin install paperclip-agent-companies-plugin
```

Pin a specific version if you want determinism:

```bash
npx paperclipai plugin install paperclip-agent-companies-plugin --version 0.9.1
```

> Plugin hot-loads on install — **no server restart required.** The Paperclip server picks the new plugin up immediately and flips it to `status: "ready"`. Confirm with:
>
> ```bash
> curl -s http://127.0.0.1:3100/api/plugins | python3 -m json.tool
> ```
>
> Look for `"pluginKey": "paperclip-agent-companies-plugin"` with `"status": "ready"` and `"lastError": null`.

If the API isn't your style, confirm in the UI: **Settings → Plugins** should list `paperclip-agent-companies-plugin v0.9.x` as ready. The plugin's own README and changelog live at https://github.com/alvarosanchez/paperclip-agent-companies-plugin.

### What you should see after Phase 2

✅ **Settings → Plugins** lists the plugin as ready (`v0.9.x`).
✅ **Settings** sidebar has a new **Repository Catalog** entry (registered by the plugin's `agent-companies-settings` slot). Older docs may call this "Agent Companies" — same thing, the v0.9.x plugin display name changed.
✅ Dashboard / "Companies" view is **still empty.** That's correct — the plugin is installed but you haven't pointed it at a source yet. Phase 4 does that.

If the dashboard suddenly has stuff in it after a plugin install, something's wrong — Paperclip doesn't auto-discover repos on disk. Sources are added explicitly in Phase 4.

### Phase 2 — what the plugin schedules automatically

Once `status: "ready"`, the plugin registers an hourly cron job `catalog-auto-sync` (`0 * * * *`) that re-syncs every tracked source. That's why the runbook only tells you to "add the source once" in Phase 4 — drift gets auto-corrected within the hour. Disable per-source from the Repository Catalog page if you prefer manual sync during iteration.

## Phase 3 — Wire the secrets the shell adapter needs (~5 min)

Active employees in [`../COMPANY.md`](../COMPANY.md) declare an `envPassthrough` list per adapter. Paperclip needs to know the values for each listed env var, otherwise the shell adapter will fail when the runner tries to read them.

**Option A — Paperclip secrets store (recommended for local).** UI: **Settings → Secrets → Add secret**. Add each of:

| Secret name | Value | Used by | Notes |
|---|---|---|---|
| `LLM_API_KEY` | your provider API key | both meta-agents | OpenRouter / Anthropic / OpenAI / whichever you use |
| `LLM_BASE_URL` | e.g. `https://openrouter.ai/api/v1` | both meta-agents | Skip if you set per-agent overrides |
| `LLM_MODEL` | e.g. `anthropic/claude-sonnet-4.5` | both meta-agents | Default fallback model |
| `LLM_MODEL_SELF_IMPROVER_ISSUES` | per-agent override | `self-improver-issues` only | Optional |
| `LLM_MODEL_ISSUE_IMPLEMENTER` | per-agent override | `issue-implementer` only | Optional |
| `GH_TOKEN` | GitHub PAT with `repo` scope | both meta-agents | Needs issues + PR permissions on the IndexFlow repo |
| `AGENT_NETWORK` | `sepolia` | both | Meta-agents don't need a live RPC — `sepolia` for sanity |
| `AGENT_NON_INTERACTIVE_WRITE_EXECUTE` | `1` | both | Suppresses TTY prompts inside the shell adapter |
| `AGENT_MAX_TURNS` | `20` | both | Sensible cap for first-test runs |

**Option B — shell env (fastest for a one-off test).** Just `export` each var in the shell that runs `npx paperclipai run`. Less secure (visible to other processes via `/proc/<pid>/environ`); fine for the first smoke test, migrate to Paperclip secrets before any sustained use.

**Verify** by running `npx paperclipai env` — it should print every env var Paperclip resolves from your config + secrets store.

## Phase 4 — Import the IndexFlow company (~5 min)

### 4a. Generate the Paperclip-native mirror (one-time + after canonical edits)

The plugin requires a per-slug subfolder layout (`agents/<slug>/AGENTS.md`)
that our canonical `agents/*.md` flat files don't match. We solve this with
a generated mirror at [`paperclip/companies/indexflow/`](../paperclip/companies/indexflow/).

```bash
# Generates COMPANY.md + agents/<slug>/AGENTS.md mirror from canonical sources.
# Idempotent — clean rebuild every run.
npm run sync:paperclip
```

Run this **once** before the first source-add, and **after any edit** to
`COMPANY.md` or to a mirrored agent prompt (`agents/self-improver-issues.md`,
`agents/issue-implementer.md`). The mirror is git-tracked so the script
isn't required for read-only imports from a GitHub URL — but it IS required
locally any time the canonical sources change.

See [`paperclip/README.md`](../../paperclip/README.md) for why the mirror
exists and how to add a new agent to it.

### 4b. Add the mirror as a Paperclip source

In the Paperclip UI:

1. **Settings → Repository Catalog → Add source.** Pick one URL:

   | URL form | When to use |
   |---|---|
   | **Local checkout (recommended for iteration)** — bare absolute path: `/Users/reuben/Desktop/minestarters/code/snx-prototype/paperclip/companies/indexflow` | Reads your working tree directly (no `git clone`), so post-`sync:paperclip` edits are visible immediately. Every regenerate + UI **Sync** click pulls them in. |
   | **GitHub URL** — `https://github.com/reubenr0d/indexflow-prototype` (or shorthand `reubenr0d/indexflow-prototype`) — the plugin will shallow-clone, find `paperclip/companies/indexflow/COMPANY.md`, and import from there | More stable across machines. Changes must be **committed and pushed** before the plugin sees them. |

   > **DO NOT use a `file:///…` URL.** The plugin's `looksLikeLocalPath()` only matches `/`, `./`, `../`, `~/`, or `C:\`-style prefixes. A `file:///` prefix gets routed through the **git clone** path, which (a) fails for non-git directories, (b) silently reads the last committed state (missing post-`sync:paperclip` edits) when it does work, and (c) typically fails Import with `"Company not found."` because the cloned repo state can't be matched back to the discovered company ID. Use the bare absolute path.

   > **DO NOT point the source at the repo root** (`/Users/reuben/Desktop/minestarters/code/snx-prototype`). The plugin's recursive walker would discover BOTH the canonical root-level `COMPANY.md` (which imports with **"No structured contents detected"** because canonical agent files are at the wrong paths for the v0.9.x classifier) AND the mirror's `COMPANY.md` — two "IndexFlow" companies with conflicting state. Point at the mirror subdirectory only.

2. **Discover** — the plugin scans the mirror root for `COMPANY.md` files matching `schema: agentcompanies/v1`. It should find exactly one (IndexFlow, version 0.3.0).

3. **View contents** — should now show the 2 mirrored agents (`self-improver-issues`, `issue-implementer`) under the "Agents" group. If you still see **"No structured contents detected"**, you almost certainly added the repo root rather than the mirror subdirectory — remove the source and re-add with `/…/paperclip/companies/indexflow` (see Phase 4 troubleshooting).

4. **Import as new company** — creates an `IndexFlow` company in Paperclip with:
   - **2 active runnable employees** (mirrored): `self-improver-issues`, `issue-implementer`
   - The 2 **prompt-only risk officers** (`risk-officer-self-improvement`, `risk-officer-self-improvement-issues`) stay documented in `COMPANY.md` `employees:` but are NOT mirrored — they have no heartbeat and are invoked inline by `scripts/run-self-improvement-*-risk-officer.mjs`. Visible in the org-chart YAML but not as runnable Paperclip agents.
   - The brainstorm slate (`content-publisher`, `partnership-tracker`, `broadcast-bot`, `docs-syncer`, `basket-ideator`) and the backlog slate (`vc-outreach-agent`, `lp-outreach-agent`, etc.) live in `COMPANY.md` as YAML blocks and are visible in the company manifest viewer, but won't appear as importable agents until they're promoted (prompt file authored + added to `ACTIVE_RUNNABLE_EMPLOYEES` in `scripts/sync-paperclip-mirror.mjs` + re-synced). The brainstorm-promotion campaign for the 5 brainstorm agents is scoped as 11 GitHub issues (`gh issue list --label brainstorm-promotion`) — see [Phase 4d — Brainstorm promotion campaign](#phase-4d--brainstorm-promotion-campaign-open-issues) below.
   - **Trading agents should NOT appear**: `vault-manager`, `mining-manager`, `quality-matrix-manager`, trading `risk-officer`. They're documented under `COMPANY.md` §Out of Scope and are intentionally absent from the mirror.

5. **Enable daily auto-sync (overwrite mode is the plugin default).** Repo is canonical; any drift in the Paperclip company state gets overwritten on the next sync.

### Phase 4 troubleshooting

| Symptom | Fix |
|---|---|
| **"No structured contents detected" + "Company not found." on Import** | Source is pointing at the repo root, not the mirror. The plugin's v0.9.x classifier requires `agents/<slug>/AGENTS.md` (per-slug subfolder, plural capital S), but the canonical layout is flat `agents/<slug>.md`. Remove the source and re-add as `…/snx-prototype/paperclip/companies/indexflow` (the mirror). Then `npm run sync:paperclip` first if you haven't yet. |
| "No companies discovered at source" | Confirm `paperclip/companies/indexflow/COMPANY.md` exists (run `npm run sync:paperclip`). The frontmatter must include `schema: agentcompanies/v1`. |
| **"Company not found." on Import (with structured contents visible — the 2 agents show under View Contents but every Import click fails)** | This is the v0.9.1 UI ↔ plugin contract bug: the UI's Import button sends `{ companyId: <paperclip-uuid>, params: { companyId: <source-id>, selection: ... } }`, but the Paperclip server forwards the raw body to the worker without unwrapping `params`. The worker reads `rawParams.companyId` — picks up the Paperclip-UUID instead of the source-id, fails `findRepositoryCompany`, throws `"Company not found."`. **Workaround**: bypass the UI button entirely and run `npm run paperclip:import` from the repo root. The script reads the catalog state, calls `catalog.prepare-company-import` with the correct flat body, POSTs the prepared source to `/api/companies/import` (the same endpoint the UI calls after prepare), and links the source via `catalog.record-company-import` so future hourly auto-syncs work. See [`scripts/paperclip-direct-import.mjs`](../scripts/paperclip-direct-import.mjs) for the full repro + bug analysis. Idempotent; safe to re-run. |
| **Discovered company is missing recent edits I just made to `COMPANY.md` or `agents/*.md`** | (a) Re-run `npm run sync:paperclip` to refresh the mirror — canonical edits don't propagate until the script runs. (b) If using GitHub URL, also commit + push. (c) Switch to local bare absolute path to read the working tree directly. (d) After regen, the plugin's hourly auto-sync (`0 * * * *`) will pick the changes up; click the source's **Sync** button to force it immediately. |
| **An older mirror file shows in the UI even after re-running sync** | The plugin caches scans. Click the source's **Sync** button in the Repository Catalog page to force a re-scan. |
| **Plugin worker logs `file:/// rejected by looksLikeLocalPath`** | You used a `file:///…` URL instead of a bare path. The plugin's `looksLikeLocalPath` (worker.js v0.9.1 line 17136) doesn't recognise `file://`, so it routes through git-clone and the company-ID mismatch surfaces only at Import time. Use the bare absolute path. |
| Trading agents appear in the company | They shouldn't — the mirror only includes the 2 active runnable employees. If you somehow see them, your source is pointing at the repo root (not the mirror) AND a future plugin upgrade started recognising the flat layout. Re-point at the mirror subdir. |
| Plugin import button greyed out | Confirm the plugin hot-loaded with `curl -s http://127.0.0.1:3100/api/plugins` — `status` should be `"ready"`. If `"pending"` or `"error"`, check `lastError` in that response; full server restart (`pkill -f 'paperclipai onboard' && npx paperclipai run`) is the nuclear option. |

### Phase 4b — alternative: import via the workaround script (`npm run paperclip:import`)

If the UI Import button keeps failing with `"Company not found."` despite the source being correctly pointed at the mirror and View Contents showing the 2 agents, run the workaround script directly:

```bash
npm run paperclip:import
```

What it does (verified working against Paperclip server + plugin v0.9.1 on 2026-05-26):

1. Auto-discovers the plugin id from `/api/plugins`.
2. Reads the plugin's catalog state to find the source company (`repo-XXXXXXXX:COMPANY.md`).
3. Reads `/api/companies` to find the target Paperclip company (defaults to the one named "Indexflow" — override with `PAPERCLIP_TARGET_COMPANY_ID`).
4. Calls `catalog.prepare-company-import` with a flat body (the shape the UI should have sent) to get the prepared import source.
5. POSTs the source to `/api/companies/import` with `target.mode = "existing_company"` — same call the UI makes after prepare.
6. Calls `catalog.record-company-import` to link source ↔ target so the hourly `catalog-auto-sync` cron keeps the company in sync.
7. Verifies by listing the agents on the target.

Expected output ends with:

```
=== Verify agents now present in Paperclip
  Paperclip company "Indexflow" now has 3 agents:
    - CEO (role=ceo, adapter=claude_local, status=error)
    - issue-implementer (role=agent, adapter=process, status=idle)
    - self-improver-issues (role=agent, adapter=process, status=idle)
```

The import is **idempotent** — re-running after the agents already exist re-creates them with the `replace` collision strategy, which mirrors what the UI does. After the agents land, you **must** wire each one's `process`-adapter `command`/`args`/`cwd`/`env` — the plugin import does not do this for you (see Phase 4c below).

### Phase 4c — Configure the process adapter (REQUIRED, ~30 sec)

Newly imported agents land with `adapterType: "process"` and an `adapterConfig` containing only the managed-instructions paths — **no `command`, `args`, `cwd`, or `env`**. The plugin import deliberately does not apply the `employees[].adapter` block from [`../COMPANY.md`](../COMPANY.md), because that block describes how to invoke the runtime (`scripts/agent-runner.mjs`) on the operator's machine, not how to render the agent. The next manual heartbeat would otherwise fail with:

```
Process adapter missing command
```

Run the configure-adapters script to PATCH the missing fields onto every active runnable employee in one shot:

```bash
npm run paperclip:configure-adapters
```

What it does (see [`../scripts/paperclip-configure-adapters.mjs`](../scripts/paperclip-configure-adapters.mjs)):

1. Resolves the IndexFlow company via `/api/companies` (override with `PAPERCLIP_TARGET_COMPANY_ID`).
2. Loads `/api/companies/:id/secrets` to map each `envPassthrough` name to its `secretId`.
3. For each active runnable employee declared in the script:
   - PATCHes `/api/agents/:id` with `adapterConfig: { command: "npm", args: ["run", "agent:run", "--", <slug>], cwd: <repo root>, env: { ...secret_refs } }`.
   - Paperclip's PATCH route merges adapter config by default (no `replaceAdapterConfig: true`), so the managed-instructions keys the import set are preserved.
4. **Idempotent**: re-running after the agents are already configured is a no-op (logs `already configured (no change)`).
5. Missing required secrets are warned but the PATCH still proceeds; missing optional secrets (e.g. `LLM_MODEL_SELF_IMPROVER_ISSUES`) are noted as fine.

Equivalent values if you prefer the Paperclip UI (Settings → Agent or directly on the agent card):

| Agent | command | args | cwd | env keys to bind (values come from Settings → Secrets) |
|---|---|---|---|---|
| `self-improver-issues` | `npm` | `["run", "agent:run", "--", "self-improver-issues"]` | repo root | `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_MODEL_SELF_IMPROVER_ISSUES`, `GH_TOKEN`, `AGENT_NETWORK`, `AGENT_NON_INTERACTIVE_WRITE_EXECUTE`, `AGENT_MAX_TURNS` |
| `issue-implementer` | `npm` | `["run", "agent:run", "--", "issue-implementer"]` | repo root | `LLM_API_KEY`, `LLM_BASE_URL`, `LLM_MODEL`, `LLM_MODEL_ISSUE_IMPLEMENTER`, `GH_TOKEN`, `AGENT_NETWORK`, `AGENT_NON_INTERACTIVE_WRITE_EXECUTE`, `AGENT_MAX_TURNS` |

The full post-import workflow is therefore:

```bash
npm run paperclip:import && npm run paperclip:configure-adapters
```

The mirror's [`paperclip/companies/indexflow/.paperclip.yaml`](../paperclip/companies/indexflow/.paperclip.yaml) carries the `command`/`args` half (generated by `npm run sync:paperclip`) so future plugin builds that fully honour the portable `agents[].adapter.config` block will need less of the configure-adapters script — but as of plugin v0.9.1 the script is still required to fill machine-specific `cwd` and bind `env` to secret_refs.

### Phase 4d — Brainstorm promotion campaign (open issues)

## Phase 5 — First heartbeat (~5 min)

The cleanest "is this actually working?" smoke test is to manually trigger `self-improver-issues`.

> **Why this agent for the first test?**
> Lowest blast radius. `self-improver-issues` drafts proposals into `.agent-self-improvement/proposed-issues.json` *then* the issue risk-officer vets the manifest *before* `scripts/apply-self-improvement-issues.mjs --open-issues` calls `gh issue create`. Worst case if anything misfires: a draft JSON file lands on disk. No PRs, no on-chain calls, no public posts.
>
> Don't test `issue-implementer` first — it's callback-only (`schedule: null`, triggered by `/agent implement` on a GitHub issue). Test it later by labeling one of the issues `self-improver-issues` files and replying `/agent implement`.

### Phase 5 troubleshooting

| Symptom | Likely cause | Fix |
|---|---|---|
| Run fails immediately with `Process adapter missing command` and a stdout warning `No project or prior session workspace was available. Using fallback workspace "…/instances/default/workspaces/<agent-id>"` | Phase 4c was skipped — the import landed an agent whose `adapterConfig` has no `command`/`args`/`cwd`. The fallback-workspace message is a secondary warning, not the root cause. | Run `npm run paperclip:configure-adapters` (idempotent). Re-run the heartbeat. |
| Run fails immediately with `ENOENT` | Adapter `cwd` doesn't resolve to the repo root | Either re-run `npm run paperclip:configure-adapters` (auto-detects repo root from the script location; override with `PAPERCLIP_REPO_ROOT`) or edit `adapterConfig.cwd` directly in the UI to `/Users/reuben/Desktop/minestarters/code/snx-prototype` |
| Run fails with `LLM_API_KEY undefined` | Phase 3 secrets not loaded by the adapter | Add the secret in Settings → Secrets, then re-run `npm run paperclip:configure-adapters` so the agent's `env` bindings repoint at the new `secretId` |
| Run hangs without producing output | `AGENT_NON_INTERACTIVE_WRITE_EXECUTE` not set to `1` — runner is waiting for TTY input | Add the secret per Phase 3 and re-run |
| `paperclip-heartbeat.json` not written but run succeeded in UI | Dry-run mode is on, or `AGENT_VAULT_OVERRIDE` was set — both gate the write | Confirm neither `DRY_RUN=1` nor `AGENT_VAULT_OVERRIDE=...` is in the adapter env |
| `gh: command not found` partway through | Runner tried to call `gh` for issue context | `brew install gh && gh auth login` (one-time, on the operator's machine) |

## Phase 6 — Decide on Paperclip-vs-CI cron parity (~5 min)

The `self-improver-issues` routine in `COMPANY.md` is `state: paused` because the existing hourly cron in `.github/workflows/vault-agent.yml` is canonical today. Two acceptable end states — pick one, don't run both:

### Option A: Keep Paperclip as a dashboard (default, lowest risk)

Paperclip surfaces the runs that CI drives. You use the UI for visibility + the occasional manual re-run. Leave the routine `paused`.

**Pros**: Zero risk of duplicate runs racing on the same proposal manifest. CI cron is battle-tested. Paperclip is purely additive.

**Cons**: You don't get Paperclip's scheduler benefits (budget-driven pause-on-overrun, per-employee cost caps as hard stops).

### Option B: Cut over to Paperclip cron

Flip `state: paused` → `state: enabled` in `COMPANY.md`'s `routines[]` entry for `self-improver-issues`, **and** disable the corresponding step in `.github/workflows/vault-agent.yml`. Two changes that must land together.

**Pros**: Single scheduler. Paperclip enforces the per-employee monthly budget cap as a hard stop (CI doesn't).

**Cons**: Failure modes shift from "GitHub Actions cron skipped/queued" to "your local machine was asleep when the heartbeat was due". For production use, that's a reason to run Paperclip on a small VM rather than locally.

**Don't run both** — they'll race on `.agent-self-improvement/proposed-issues.json` and produce duplicate GitHub issues.

## Optional Phase 7 — Beyond local

> **Scope decision (2026-05-26):** Cloud-hosting Paperclip is **explicitly out of scope** for the public-transparency roadmap. The public mirror is [`apps/web/src/app/ops/page.tsx`](../apps/web/src/app/ops/page.tsx) (live at [`indexflow.app/ops`](https://indexflow.app/ops)) which reads `COMPANY.md`, `agents/memory/`, `growth/`, and `AGENT_DEPLOYMENT_MEMORY.md` directly from this git repo. That covers every "show people how the company runs" use case without the cloud-Paperclip risk surface (auth, secrets in a Postgres outside the founder's machine, public dashboard subject to scraping, etc.).
>
> Local Paperclip per Phases 1–6 above is the founder's private UI: tickets, monthly budget enforcement, manual re-runs, approval queues for the engineering meta-agents. It is **not** the public surface. Keep it on `local_trusted` per the runbook default.

If a future phase ever justifies moving Paperclip off the founder's machine (multi-operator team, hosted ticket inbox needed, etc.), the path is well-trodden — but it requires a fresh scope decision and explicit user approval in-session, not a default upgrade.

| Concern | Local (current, recommended) | Production (out of scope until re-justified) |
|---|---|---|
| **Database** | Embedded PG (auto-created at `~/.paperclip/instances/default/db`) | `DATABASE_URL=postgresql://user:pass@host:5432/paperclip` (PG 17+) |
| **Storage** | Local disk (auto-created at `~/.paperclip/instances/default/data/storage`) | `STORAGE_PROVIDER=s3` + `S3_BUCKET`/`S3_REGION`/`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY` |
| **Auth mode** | `local_trusted` (no login) | `DEPLOYMENT_MODE=authenticated` + `BASE_URL=https://paperclip.example.com` |
| **Process model** | `npx paperclipai run` (or `npx paperclipai onboard --yes` for first boot) from terminal | Docker (`docker-compose.quickstart.yml`) or any Node-friendly platform; once globally installed (`npm install -g paperclipai`) the `npx` prefix can be dropped |
| **Tunnelling for solo-operator access on the go** | Not needed | Tailscale (run `npx paperclipai run --bind tailnet` and connect via Tailscale-assigned IP) |
| **Public visibility** | None — local-only | None — Paperclip's UI is for operators, not the public. Public visibility belongs to `/ops`. |

**If a future cloud deploy is re-justified**, per [`../AGENTS.md`](../AGENTS.md) §Deployment Safety Rules:

1. Add the new resource to [`../AGENT_DEPLOYMENT_MEMORY.md`](../AGENT_DEPLOYMENT_MEMORY.md) **before** creating it (planned row, just like the current local Paperclip row was).
2. Surface the deploy plan to yourself explicitly — no agent should auto-create cloud resources without your in-session approval.
3. Update this runbook with the production-specific steps (DATABASE_URL setup, S3 bucket creation, DNS, TLS, Tailscale bootstrap, etc.) once you've done it once.
4. **Confirm the public-mirror story still holds**: cloud Paperclip should never replace [`/ops`](https://indexflow.app/ops) as the public-facing surface. The `/ops` page's data source is `git pull`; cloud Paperclip's UI would be a *second* surface with its own auth and risk profile, not a substitute.

The local-trusted-only mode is intentionally the default for v1. Skipping straight to cloud is a meaningful additional risk surface (auth, network, secrets management) that the dashboard's value-add doesn't yet justify — and the public mirror has already absorbed the use case that *would* have justified it.
