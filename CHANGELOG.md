- [2026-05-22 23:30 UTC+05:30] **Envio HyperIndex re-wired to the app: dashboard / portfolio / baskets / chains pages no longer show zero values when deposits exist on-chain.** Root cause: every handler `eth_call` in `apps/envio/src/utils/contractCalls.ts` was hitting `https://*.rpc.hypersync.xyz`, which is Envio's value-added RPC and requires an `ENVIO_API_TOKEN` Bearer header (verified by curl: `{"error":"Your token is malformed..."}`). The reads were wrapped in silent `try/catch` blocks, so every basket/vault state field that needed an on-chain read silently fell back to the zero defaults — `Basket.sharePrice/usdcBalanceUsdc/tvlBookUsdc/totalSupplyShares/perpAllocatedUsdc/depositFeeBps/redeemFeeBps/minReserveBps/maxPerpAllocation/assetCount` all `"0"`, `VaultStateCurrent.registered = false` even after `vaultRegistered` activity events fired, `BasketExposure` empty, `BasketSnapshot` rows zero, `ChainPoolState` empty (so the `/chains` page was permanently blank). Cumulative counters (`Basket.cumulativeDepositedUsdc`, `UserBasketPosition.shareBalance/netDepositedUsdc`) were correct because those are incremented from event params. The fix:
  - `apps/envio/src/utils/contractCalls.ts` now resolves each chain's RPC URL via env (`SEPOLIA_RPC_URL`, `FUJI_RPC_URL`, `ARBITRUM_SEPOLIA_RPC_URL`, `HUB_RPC_URL`, `SPOKE_RPC_URL`) with public-RPC fallbacks (`https://ethereum-sepolia-rpc.publicnode.com`, `https://avalanche-fuji-c-chain-rpc.publicnode.com`, `https://arbitrum-sepolia-rpc.publicnode.com`, plus the dual-Anvil locals). If a `*_RPC_URL` is pointed at a `https://*.rpc.hypersync.xyz` host, the `http()` viem transport is configured with `fetchOptions: { headers: { Authorization: "Bearer ${ENVIO_API_TOKEN}" } }` so the token only attaches where it's needed.
  - Every `readContract` call site swaps its bare `catch {}` for `catch (error) { warnOnce(chainId, "<Contract.fn>", error); }` so future regressions surface as a one-shot `console.warn` per `(chainId, op)` pair instead of silently leaving entity fields at zero. `warnOnce` dedupes via a module-level `Set<string>` keyed on `${chainId}:${op}`.
  - Replaced the per-target fan-out in `apps/web/src/hooks/usePoolReserveRegistry.ts` with a single `useQuery` against the unified Envio endpoint. Envio's GraphQL endpoint already serves rows for all indexed chains keyed by `chainSelector`; the old `useMultiChainSubgraphQuery` fan-out was issuing N identical requests to the same URL and concatenating duplicate rows into the chart. Hook signature changed from `failedTargets: DeploymentTarget[]` (always empty under the unified endpoint) to `isError: boolean`; `apps/web/src/app/chains/page.tsx` now shows a single `"Could not reach the indexer..."` banner when the query errors, and the surrounding test (`apps/web/src/app/chains/page.test.ts`) plus the hook test (`apps/web/src/hooks/usePoolReserveRegistry.test.ts`) were rewritten to mock `useQuery` directly and assert the new shape — 5 chains-related tests still green out of the suite's 78 passing.
  - `apps/web/src/hooks/useHeroProtocolStats.ts` `fetchChainBaskets` was calling `GET_BASKETS_OVERVIEW` with `{ first, skip }` but the query declares `$chainId: Int!`, so the "all chains" hero stats route was throwing a Hasura validation error and silently returning `null`. Added `chainId: chainIdForDeploymentTarget(target)` (matches the pattern in `useMultiChainBaskets`) and imported `chainIdForDeploymentTarget` alongside `DeploymentTarget`.
  - `apps/web/src/lib/subgraph/envio-queries.ts` `ENVIO_GET_BASKET_DETAIL` now declares `$activityFirst: Int!, $activitySkip: Int!` and threads them into `activities(limit: $activityFirst, offset: $activitySkip, ...)` — previously the variables were sent by the call site and silently ignored against a hardcoded `limit: 100`.
